## 一、实现内容

`prototype/mac/Sources/ScreenSender.swift`：

### 1.1 RateSignals

```swift
struct RateSignals {
    var droppedDelta: Int     // 本轮在途丢帧增量
    var inFlight: Int         // 本轮观察到的在途帧数
    var encodeMs: Double      // 本轮平均编码耗时（Phase 1 用均值代替 p95）
    var sentMbps: Double      // 本轮实际发送码率
    var captureFps: Double    // 本轮采集帧率
}
```

### 1.2 健康度

```swift
budgetMs = 1000.0 / captureHz
encodeLoad = encodeMs / budgetMs
inflightLoad = inFlight / 2.0
dropLoad = droppedDelta > 0 ? 1.5 : 0.0
health = max(encodeLoad, max(inflightLoad, dropLoad))
```

### 1.3 控制律

- `captureFps < 10`：静态桌面，清空连续计数并返回
- `health > 1.0` 连续 2 轮：`current = max(15, current * 0.80)`
- `health < 0.70` 连续 3 轮且 `current < target`：`current = min(target, current * 1.10 + 1)`
- 死区：`abs(next - current) < max(2, current * 0.05)` 不改
- 每次变更调用 `encoder.setBitrate` 并打日志

### 1.4 调用点

2 秒统计 Timer 里先算 `encAvg`、`capturedDelta`、`droppedDelta`，再调用
`rateCtl.tick(RateSignals(...))`，然后用同一批值打印原有统计行。

## 二、实测

`budgetMs=16.67`，初始码率 180 Mbps。

## 三、发现的问题（重要）

### 3.1 降幅过大，码率一路滑到接近下限

健康度只比 1.0 高一点（1.05 到 1.23），却触发了一次又一次 20% 下调，
180 Mbps 在约 36 秒内跌到 17 Mbps。画面质量会明显下降，但编码延迟并没有因此回落，
说明这类负载下延迟不是码率造成的，继续降码率只是伤质量。

### 3.2 静止后不会回升

`captureFps < 10` 时直接返回，不累积 `lowRounds`。运动结束、桌面静止后，
码率会停在 17 Mbps 不动。实测重启发送端才恢复到 180。

### 3.3 健康度数值与统计行编码延迟不一致

统计行显示编码延迟 50 到 78 ms，按 `budgetMs=16.67` 应得到 3.0 到 4.7 的
`encodeLoad`，但日志里的健康度只有 1.05 到 1.23。两者用的是同一个 `encAvg`，
需要下轮排查是采样窗口、重置时机还是计数口径的问题，本轮未定位。

## 四、结论

- 控制律本身跑通，健康度能驱动码率变化，日志可追溯
- 当前阈值（1.0 / 0.7）和降幅（20%）对这个负载过于激进，建议：
  - 降幅改为 10%，或加「降码率后健康度未改善则停止继续降」的保护
  - 静止时若 `current < target`，允许每 6 秒小幅回升
  - 先修 3.3 的口径问题，否则阈值判断建立在错误数值上
- 本轮不做协议改动，未涉及 Windows 侧

## 五、下一步建议

1. 修 `encAvg` 与健康度不一致（优先，影响所有判断）
2. 降幅 20% → 10%，并加连续下调次数上限
3. 静止回升：`captureFps < 10` 时也允许每 3 轮 +10%
4. 用 `--pace` 稳定内容复测，确认 p95 与 fps 不劣化

## 六、第二轮调整（2026-11-12）

针对第三节的问题做了收敛，提交见 git log `fix(mac): 收敛 Phase1 降幅与静止回升，码率按分辨率估算`。

### 6.1 3.3 的澄清

重看同一轮日志后确认，健康度与编码延迟口径一致：

```
[99962.322] 健康度 1.08（编码 108% 在途 0%）...
[99962.322] 采集 244 ... 编码延迟 18.1 ms
```

18.1 / 16.67 = 1.086，与 1.08 完全对得上。之前误把 motionloader 启动初期
50 到 78 ms 的那一段当成了同一时段。**3.3 不成立，无需修改采样口径。**

### 6.2 控制律调整

| 项 | 调整前 | 调整后 |
|---|---|---|
| 下调阈值 | health > 1.0 | health > 1.15 |
| 单次降幅 | 20% | 10% |
| 降档冷却 | 无 | 10 秒 |
| 静止行为 | 直接返回，不回升 | 每 3 轮（约 6 秒）回升 10% |

### 6.3 默认码率

固定 180 Mbps 改为按像素率估算，`0.35 bit/pixel/frame`：

| 分辨率与帧率 | 估算码率 |
|---|---|
| 1600x1000@60 | 约 34 Mbps |
| 2240x1400@60 | 约 66 Mbps |
| 2880x1800@45 | 约 82 Mbps |

仍可用 `SECDISPLAY_MBPS` 覆盖。降低默认值的理由是原 180 Mbps 对多数档位都偏富余，
且一次下调就是几十 Mbps，观感突兀。

### 6.4 验证状态

编译通过。运行验证被上一轮强杀留下的孤儿虚拟屏挡住：进程已退出，但 WindowServer
仍保留 `vendor=0xeeee` 的显示条目，`run.sh restart` 按保护逻辑拒绝启动。
需要注销重登或重启 WindowServer 清理，清理后补测：

1. motionloader 60 秒，确认降幅为 10% 且两次下调间隔不小于 10 秒
2. 运动结束后静止 30 秒，确认码率逐步回升
3. 确认默认码率落在 30 到 40 Mbps 区间

### 7.3 降档曲线评估

现象：33 Mbps 一路降到 18（累计 -45%），期间健康度长时间停在 6.93
（编码延迟约 115 ms，统计行 103.9~116.1 ms 区间），连续 4 次下调对编码延迟毫无改善。

结论：**降幅 10% 与冷却 10 秒本身验收通过，不建议本轮再动；低档地板问题留到 Phase 2。**

理由：

1. 下调是正确方向但无效。该负载（motionloader 60）的编码延迟由内容复杂度
   与虚拟屏像素率决定，与码率弱相关，所以健康度不随码率下降而回落，
   控制律只能一路降到底。第二轮已预见此风险（3.1 节），本轮实测坐实。
2. 三个候选里，「健康度极高时降幅更大但次数更少」暂时反对。它引入第二套
   控制参数，而当前健康度对"编码延迟 vs 码率"的因果没有区分能力，
   更大的降幅会在延迟恰好可降的场景里过冲。
3. 「1600x1000 不低于 25 Mbps 的地板」方向合理但数字存疑。本轮 18 Mbps
   时峰值 fps 仍有 55，未见丢帧，说明 18 尚未造成可观测的质量损失；
   25 这个数需要先测出"多少 Mbps 开始丢帧或明显糊"再定，不能拍脑袋。
4. 更值得做的是：连续 N 次下调后健康度无改善，就停止下调（熔断）。
   这不改变单步降幅，只阻止无意义的滑落，与第一轮 3.1 节的建议一致。

### 7.5 验收结论

四判据全部通过，Phase 1 验收通过。遗留事项：

- 虚拟屏运行中消失（环境问题，需查 run.sh 保护逻辑与 WindowServer 状态）
- 编码延迟型负载下降码率无效，建议加"连续下调无改善即熔断"
- 在途/丢帧路径未被本轮负载覆盖
