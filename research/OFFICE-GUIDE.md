# 办公使用指南

针对"要能高效办公"这个目标，说清楚什么能做、什么做不到、怎么调。

---

## 一、先明确一个前提

**办公场景里，延迟和画质的要求是不一样的。**

| 用途 | 延迟容忍 | 画质要求 |
|---|---|---|
| 写文档、看代码 | 50ms 都无感 | 文字清晰，小字不发虚 |
| 浏览网页、聊天 | 30ms 以内舒服 | 一般 |
| 看图表、对照资料 | 30ms | 数字要能认 |
| 拖窗口、滚动 | 20ms 以内才跟手 | 滚动时不糊 |
| 视频会议 | 30ms | 人脸清楚即可 |
| 游戏 | 不可能 | — |

**结论：办公场景真正的门槛是"文字清晰度"，不是极致延迟。**

现有架构的延迟（完整链路估算 8~26ms）对办公完全够用。真正需要下功夫的是画质。

---

## 二、画质为什么会差

按影响程度排。

### 2.1 分辨率没对齐（影响最大，也最容易修）

虚拟屏的**像素尺寸必须等于 Windows 屏的物理像素**。

如果你的 Windows 是 2240x1400，而 Mac 端配的是 2560x1600，macOS 会先把画面缩放到 2240x1400 再编码。这一缩，文字边缘的像素就被平均掉了。

**检查方法：** Windows 上「设置 → 系统 → 显示 → 高级显示 → 显示信息」，看"桌面分辨率"。

### 2.2 码率不够

H.264 压桌面文字是最吃亏的。字边缘全是高频细节，压缩算法倾向于把这些细节抹平。

| 码率 | 2240x1400 下的观感 |
|---|---|
| 20 Mbps | 明显模糊，小字看不清 |
| 60 Mbps | 能用，但小字发虚 |
| **120 Mbps** | **清晰，接近原生** |
| 200 Mbps | 基本无差别 |

千兆网理论上限 940 Mbps，给 120~200 完全安全。

### 2.3 色度抽样（H.264 的固有缺陷）

H.264 默认 4:2:0：亮度全分辨率，色度只有一半。**黑字白底时字边缘会出现彩色毛边。**

VideoToolbox 的低延迟模式只支持 4:2:0，这一项没法绕开。Duet 也一样。

**缓解办法只有提高码率**，让编码器把预算更多花在亮度细节上（人眼对亮度最敏感）。

### 2.4 Windows 端缩放设置

Windows 显示设置里的"缩放"如果是 125% 或 150%，系统会再做一次缩放。

**建议把缩放设为 100%**，让虚拟屏的像素和物理像素严格 1:1。

如果觉得 100% 下字太小，那就不要改 Windows 缩放，而是让 Mac 端的 `logicalWidth/Height` 设成一半：

```
width = 2240, height = 1400      ← 物理像素
logicalWidth = 1120, logicalHeight = 700   ← 逻辑尺寸，界面会大一倍
```

这样 macOS 用 2x 渲染，再编码成 2240x1400 送过去，文字反而更锐利。

## 三、延迟为什么会大

### 3.1 用 Wi-Fi（最常见原因）

Wi-Fi 的带宽够，但**延迟抖动大**。视频流一遇抖动就缓冲，一缓冲延迟就堆起来，而且堆上去很难落回来。

**必须接网线。** 你的笔记本没有网口，需要一个 USB 转网卡：

| 方案 | 建议 |
|---|---|
| USB 3.0 转千兆 | 30~60 元，认准 Realtek RTL8153 芯片 |
| USB-C 转 2.5G | 80~150 元，RTL8156 芯片 |

**别买十几块的杂牌**，芯片被阉割，延迟可能还不如 Wi-Fi。

### 3.2 发送队列堆积

如果发送端比接收端快，数据会堆在中间，你看到的永远是"过去的画面"，而且持续滞后。

代码里已经做了限制：在途帧数上限 2，超了就丢新帧。日志里的「在途」应该稳定在 0~2，常驻 2 说明网络在堵。

### 3.3 垂直同步

Windows 默认等垂直同步才呈现，固定多 16.6ms。代码已用 `ALLOW_TEARING` 绕过，前提是显卡支持。

启动日志里看到「免垂直同步呈现: 支持」就说明生效了。

### 3.4 电源模式

Windows 省电模式会降频，编码解码都变慢。

**设置 → 系统 → 电源和电池 → 电源模式 → 最佳性能。**

## 四、推荐的办公配置

### 4.1 Mac 端

```swift
struct Config {
    var width = 2240          // 改成你 Windows 屏的物理宽度
    var height = 1400
    var logicalWidth = 2240   // 与物理一致 = 1:1，最清晰
    var logicalHeight = 1400
    var refreshRate = 60.0
    var bitrateMbps = 120     // 有线千兆下的平衡点
    var port: UInt16 = 9922
}
```

### 4.2 自适应码率

程序会根据实际丢帧自动调整：

- 检测到拥塞 → 码率下调 20%
- 连续 6 秒无丢帧 → 回升 15%

日志里会显示 `目标 120` 这个数字在变化，说明自适应在工作。

**这意味着你不需要手动纠结码率**：给一个偏高的目标值，它会自己找到平衡点。

### 4.3 Windows 端

- 显示缩放：100%
- 电源模式：最佳性能
- 关闭不必要的后台程序

## 五、验证清单

按顺序检查，卡在哪一步就修哪一步。

```
□ Windows 端 SelfCheck.exe 全部通过
□ 两端 ping 延迟 < 1ms
□ Mac 日志显示「硬件」编码
□ Windows 日志显示「解码器就绪（硬件）」
□ Windows 日志显示「免垂直同步呈现: 支持」
□ Mac 端 width/height = Windows 桌面分辨率
□ Windows 显示缩放 = 100%
□ Mac 日志「在途」稳定在 0~2
□ Mac 日志「丢弃」增长缓慢
```

## 六、做不到的事

诚实说明边界：

| 需求 | 能否满足 |
|---|---|
| 当副屏放文档、代码、聊天 | 能 |
| 视频会议（看对方画面） | 能 |
| 看在线视频 | 能，但码率要给到 200+ |
| 玩游戏 | 不能 |
| 手写笔绘画 | 不能 |
| 触摸操作 | 不能 |
| 一套键鼠控两台 | 不能 |

---

## 七、如果还是不满意

按这个顺序调，不要一次改很多：

1. **先确认有线**，Wi-Fi 下所有优化都白费
2. **对齐分辨率**，这一项收益最大
3. **码率从 120 试到 200**，看画面变化
4. **Windows 缩放改 100%**
5. 还不够清晰 → 考虑把 `logicalWidth/Height` 设成一半开 Retina
6. 还觉得慢 → 看日志的「在途」和「丢弃」，判断是网络还是编码问题

## 八、和 Duet 的取舍

| | Duet | 本项目 |
|---|---|---|
| 订阅费 | 约 $48/年 或 $139 买断 | 免费 |
| 开箱可用 | 是 | 需要配置 |
| Windows 端稳定性 | 12 年打磨 | 未验证 |
| 延迟 | 同类水平（约 20ms）| 同类水平 |
| 画质 | 4:2:0 + 高码率 | 4:2:0 + 高码率，同一天花板 |

**画质上限是一样的**，因为都受 H.264 4:2:0 限制。差别在工程打磨和开箱体验。

如果你的核心诉求是"立刻能用于办公"，Duet 更省心。
如果你能接受一次性配置、并且想要可控，这个方案能做到同样的画质水平，成本为零。
