# 修复光标位置与点击错位：坐标系统一为逻辑点

## 现象

用户反馈「一个光标并不是实际位置」：副屏上的光标显示位置和点击落点都与预期不符，且两者偏差方向看起来不一致。

## 根因

坐标链路有四处，之前混用了两种单位。Mac 虚拟屏是 2x Retina：

- 物理像素 `2880x1800`（`cfg.width/height`）—— 用于编码、解码、呈现、全屏窗口
- 逻辑点 `1440x900`（`cfg.logicalWidth/Height`，`hiDPI=true`）—— macOS 全局坐标

`CGEvent.location`（全局鼠标）和 `CGDisplayBounds(vd.displayID)` 都在**点坐标**系里，所以 Mac 端 `CursorTracker` 发出的 `rx/ry` 本来就是 0..1440 的点值，这半段是对的。

错在 Windows 端用 `cfg.width/height`（2880x1800 物理像素）当坐标基准去解释这些值：

| 环节 | 旧代码 | 后果 |
|---|---|---|
| 光标显示 | `sx = 点坐标 / 2880 × 客户区宽` | 光标显示在真实位置的一半（越往右下越偏） |
| 输入回传 | `vx = 客户区 / 宽 × 2880` 发回 Mac | Mac 把 2880 当点坐标注入，点击被放大 2 倍 |

显示缩一半、点击放大一倍，方向相反，这就是「光标和点击各错各的」。

## 修复

两端统一用**逻辑点 1440x900** 作为坐标基准，物理尺寸仍只给编解码/呈现用，两者彻底分开。

### Windows 端

- `g_videoW/H` 更名为 `g_coordW/H`，语义明确为逻辑点坐标基准
- `ClientToVideo`、`OnCursorPacket`、光标线程全部改用 `g_coordW/H`
- `g_coordW/H` 默认取 `物理 / 2`，并新增 `--coord W H` 可在 CGDisplayBounds 返回值与预期不符时现场纠正，无需重编译
- 启动时打印「坐标基准: 逻辑 …（物理 …）」

### Mac 端

- 启动时打印实际 `CGDisplayBounds` 尺寸，与 Windows 日志对照即可确认两端一致
- 注释明确 `sendCursor` / `InputInjector` 的坐标都是逻辑点
- 换算逻辑本身不变（点坐标相减天然自洽）

## 数值验证

以光标在虚拟屏正中（逻辑点 720,450）、Windows 全屏客户区 2880x1800 为例：

```
Mac 光标点 (720,450) → Windows 屏幕 (1440,900)   ✓ 正中
Windows 点击 (1440,900) → 发回逻辑点 (720,450)   ✓ 闭环
Mac 注入 = bounds.minX + (720,450)               ✓ 同位置
```

旧代码对照：`720/2880×2880 = 720`（偏到 1/4）、`1440/2880×2880 = 1440`（放大 2 倍）。

## 现场核对方法

两端日志各有一行坐标基准，应均为 1440x900：

- Mac：`坐标基准: 逻辑点 1440x900，原点 (...)`
- Windows：`坐标基准: 逻辑 1440x900（物理 2880x1800，自动 2x）`

若 Mac 日志显示 2880x1800（说明该系统 CGDisplayBounds 返回物理像素），在 Windows 启动脚本加 `--coord 2880 1800` 即可对齐。

## 范围

本次**只修坐标系**，按用户选择不改动呈现节奏。89Hz 屏配约 43fps 输出的 2/3 刷新周期跳变（卡顿感）留待下一轮单独处理。
