# Lenovo Yoga Slim 7 Pro 14IHU5 (82NC) 适配说明

针对你的具体机器做的配置与排障。

---

## 一、这台机器的关键规格

型号 82NC = Yoga Slim 7 Pro 14IHU5，国内叫小新 Pro 14 2021 酷睿标压版。

| 项目 | 规格 | 对本项目的影响 |
|---|---|---|
| CPU | i5-11320H / i7-11370H | 够用，解码不占多少 CPU |
| 核显 | Iris Xe | **支持 MF 硬解 + D3D11 视频处理器**，能走零拷贝路径 |
| 屏幕 | **2240x1400** 60Hz（部分 SKU 是 2880x1800 90Hz）| 决定虚拟屏尺寸，见下 |
| 有线网口 | **无** | 需要用 USB 网卡，见下 |
| 无线 | Wi-Fi 6 11ax 2x2 | 能用但延迟抖动大 |
| USB-C | 支持雷电 4 / DP 输出 | 可接雷电转以太网 |

### 先确认你的屏幕是哪一块

2021 年 9 月之后有一个"高刷版"SKU，屏幕换成了 2880x1800 90Hz。

**在 Windows 上查：** 设置 → 系统 → 显示 → 高级显示 → 显示信息，看「桌面分辨率」。

| 查到 | Mac 端怎么配 |
|---|---|
| 2240x1400 | `width=2240 height=1400 logicalWidth=2240 logicalHeight=1400` |
| 2880x1800 | `width=2880 height=1800 logicalWidth=1440 logicalHeight=900` |

代码里的默认值已经按 2240x1400 预设好了。

## 二、关于"装驱动"

先澄清一个概念：**这个方案不需要在 Windows 上装任何显示驱动。**

Duet 在 Windows 上装 `DuetBus.sys` + IddCx 驱动，是因为它要让 Windows 也能当**被投屏的一端**。你的场景是 Mac → Windows 单向，Windows 只是个播放器，不需要虚拟显示器。

所以没有"装驱动才能用"这一步。真正要解决的是你说的两个问题：延迟和画质。

---

## 三、延迟大的原因与对策

### 3.1 最主要原因：你在用 Wi-Fi

这台机器没有网口。如果你现在是走 Wi-Fi 连的，那延迟大是必然的。

Wi-Fi 的问题不是带宽，是**抖动**。视频流最怕抖动，一抖就要缓冲，一缓冲延迟就堆上去，而且堆上去下不来。

**对策：接一根网线。** 三个选择：

| 方案 | 延迟 | 成本 | 建议 |
|---|---|---|---|
| USB 3.0 转千兆网卡 | 0.2~0.5ms | 30~60 元 | **推荐**，够用 |
| USB-C 转 2.5G 网卡 | 0.2~0.5ms | 80~150 元 | 更好，有余量 |
| 雷电 4 转万兆 | 0.1~0.3ms | 800 元+ | 没必要 |

**买的时候认准 Realtek RTL8153（千兆）或 RTL8156（2.5G）芯片。** 便宜的山寨网卡用的是被阉割的芯片，延迟反而不如 Wi-Fi。

### 3.2 连法

```
MacBook ──── 网线 ──── USB网卡 ──── Windows
```

或者两端都接到同一个路由器/交换机上。

直连时给两端配静态 IP：

**Mac**
```
系统设置 → 网络 → 选中网卡 → 详细信息 → TCP/IP
配置 IPv4：手动
IP：192.168.77.1
掩码：255.255.255.0
```

**Windows**
```
设置 → 网络和 Internet → 以太网 → IP 分配 → 编辑
手动 IPv4
IP：192.168.77.2
掩码：255.255.255.0
```

**验证：** Mac 上 `ping -c 10 192.168.77.2`，延迟应稳定在 1ms 以内，抖动小于 0.3ms。

### 3.3 其他影响因素

| 因素 | 影响 | 对策 |
|---|---|---|
| 发送队列堆积 | 延迟持续偏高且不回落 | 代码里已限制在途 2 帧 |
| 码率超过带宽 | 丢帧、卡顿 | 千兆网给 120Mbps 有足够余量 |
| Windows 垂直同步 | 固定多 16.6ms | 代码已用 `ALLOW_TEARING` 绕过 |
| 电源计划 | 省电模式降频 | 用「高性能」或「平衡」，别用「节能」 |

**Windows 电源设置：** 设置 → 系统 → 电源和电池 → 电源模式 → **最佳性能**。这一项对编码/解码延迟影响很实际。

## 四、画质差的原因与对策

### 4.1 分辨率没对齐（最常见）

如果你的 Mac 端配置还是默认的 2560x1600，而实际屏幕是 2240x1400，系统会缩放后再编码，**文字会被糊两遍**。

现在代码默认值已改成 2240x1400。如果你的是 2880x1800 版本，要手动改。

### 4.2 码率不够

桌面文字是 H.264 最难压的内容。字边缘全是高频细节。

| 码率 | 2240x1400 文字的观感 |
|---|---|
| 20 Mbps | 明显模糊 |
| 60 Mbps | 勉强能看，小字发虚 |
| **120 Mbps** | **清晰，接近原生** |
| 200 Mbps | 基本看不出差异 |

代码默认已改成 120 Mbps。千兆网理论上限 940，给到 200 也不挤。

### 4.3 色度抽样（H.264 的固有限制）

H.264 默认 4:2:0，色度分辨率只有亮度的一半。黑字白底这种场景会出现彩色毛边。

**目前没有好的解决办法**，因为 VideoToolbox 的低延迟模式只支持 4:2:0。能做的是提高码率让编码器把预算花在亮度细节上。

这也是 Duet 同样面对的问题，它靠的是高码率加高 Profile 来缓解。

## 五、针对这台机器的推荐配置

```swift
struct Config {
    var width = 2240          // 屏幕物理宽度
    var height = 1400         // 屏幕物理高度
    var logicalWidth = 2240   // 与物理一致，1:1 不缩放
    var logicalHeight = 1400
    var refreshRate = 60.0    // 这块屏是 60Hz；高刷版可设 90
    var bitrateMbps = 120     // 千兆网下的清晰度与流畅度平衡点
    var port: UInt16 = 9922
}
```

### 如果是 2880x1800 高刷版

```swift
var width = 2880
var height = 1800
var logicalWidth = 1440      // 开 2x Retina
var logicalHeight = 900
var refreshRate = 90.0
var bitrateMbps = 150        // 分辨率更高，码率也要给够
```

## 六、Iris Xe 的解码能力

好消息：**Iris Xe 完全够用。**

- 支持 Media Foundation 硬件 H.264 解码（Intel Quick Sync Video）
- 支持 D3D11 VideoProcessor 做 NV12 → BGRA 转换
- 2240x1400 或 2880x1800 都在能力范围内（硬解上限通常 4096x2304）

启动日志里看到 `解码器就绪 2240x1400（硬件）` 就说明走的是硬解。

如果显示的是「软件」，说明 MFT 枚举没找到硬件解码器，检查显卡驱动是否更新到最新。

---

## 七、按这个顺序排查

如果你试完还是不满意，按这个顺序看：

1. **ping 延迟**是否 < 1ms？不是就先解决网络
2. 日志里是「硬件」还是「软件」解码？软件就先更新显卡驱动
3. 日志里「丢弃」数字大不大？大就降码率
4. 日志里「在途」是否常驻 2？是就说明网络在堵
5. 分辨率是否与屏幕物理分辨率一致？
6. Windows 电源模式是不是「最佳性能」？

---

## 八、如果还有问题

把这几样发出来：

- 两端启动日志的完整输出
- `ping -c 20 <对端IP>` 的结果
- Windows 上「显示信息」里的分辨率
- 网卡的型号

这些能直接定位到是哪一环出了问题。
