# 编码器上限与帧率权衡

2026-11-08，M1 Pro，macOS 27.2。

## 结论

**VideoToolbox 的 H.264 硬编在 2880x1800 上只能稳定约 40~46fps。**
超过这个速度，帧会堆在编码器内部，延迟线性上涨。

这是 M1 Pro 视频编码单元的物理上限，不是代码问题，换 Duet 也一样。

## 实测：提交帧率对延迟的影响

隔离测试（`tools/EncLatency.swift`，不经过采集和网络，只喂合成帧）：

| 提交帧率 | 实际输出 | 提交→输出延迟（中位） |
|---|---|---|
| 30 fps | 27.5 fps | 40.0 ms |
| 40 fps | 36.7 fps | 49.4 ms |
| 50 fps | 45.3 fps | 84.3 ms |
| 60 fps | 46.5 fps | 93.3 ms |

提交超过能力上限后，延迟从 40ms 跳升到 93ms —— 多出来的全是编码器内部排队。

## 实测：完整管线的采集帧率权衡

`tools/latencyclient` 连真实发送端，`tools/motionloader` 在虚拟屏上播 GPU 动画：

| 采集上限 | 实际帧率 | 端到端中位 | p95 | 编码段延迟 |
|---|---|---|---|---|
| 60 Hz | 55.1 fps | 67.4 ms | 102.0 ms | 68 / 101 ms |
| 50 Hz | 46.0 fps | 28.0 ms | 52.3 ms | 27 / 75 ms |
| **45 Hz** | **43.1 fps** | **25.6 ms** | **49.2 ms** | **24 / 55 ms** |
| 40 Hz | 38.5 fps | 26.9 ms | 50.6 ms | 22 / 42 ms |
| 30 Hz | 29.2 fps | 24.1 ms | 44.2 ms | 21 / 41 ms |

**45Hz 是拐点**：再往上帧率涨不动，延迟翻倍。默认取 45。

## HEVC 对比

同样隔离测试，2880x1800、45fps：

| 编码 | 实际输出 | 延迟中位 |
|---|---|---|
| H.264 | 41.5 fps | 50.1 ms |
| HEVC | 41.3 fps | 58.2 ms |

**HEVC 在这个分辨率下没有性能优势**，同分辨率延迟还略高。

它有价值的场景是「同码率下画质更好」，但我们现在静态桌面只有 0.9 Mbps，
瓶颈不在码率而在编码吞吐，所以换 HEVC 收益为零，还要改两端协议，
不划算，暂不做。

## 低延迟模式验证

`EnableLowLatencyRateControl` 确实起效：同条件 50.5ms vs 不开的 59.6ms。

## 若要继续优化

按收益排序：

1. **降分辨率**：把虚拟屏设成 2560x1600，编码器能轻松跑 60fps。
   代价是非原生分辨率，文字会经过一次缩放。
2. **自适应码率/分辨率**：内容复杂时自动降档。复杂度较高。
3. **硬件升级**：M 系列后续芯片的编码器吞吐更高。

当前配置（2880x1800 @ 45Hz 采集）已经是这个分辨率下延迟与流畅度的平衡点。
