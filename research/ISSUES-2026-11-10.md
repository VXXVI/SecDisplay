## 鼠标「回不去 macOS」——架构层面，非单点 bug

现象：用户想让鼠标从副屏回到 Mac 主屏，回不去。

定性：当前协议只实现「鼠标在副屏内移动」，没有「跨越屏幕边界回到主屏」的语义。
相关链路（均已核对代码）：

- Mac `CursorTracker.tick`（`ScreenSender.swift:996`）：读 `CGEvent.location`（全局
  桌面坐标），减虚拟屏 `bounds.minX` 得相对坐标 `rx/ry`；`inside = 0<=rx<b.width`。
  鼠标回到内建主屏时 `rx<0` → `inside=false` → 发 `visible=0` 光标包。
- Windows `OnCursorPacket`（`SecDisplayReceiver.cpp:264`）：`if(!visible) return;`
  —— 直接丢弃，`g_cursorX/Y` 保留旧值，光标线程继续按旧坐标 `SetCursorPos`。
- Windows 光标线程（`:1639`）：1 秒让位守卫（本机鼠标动过就不跟随），
  且 `SetCursorPos` 反复把 Windows 光标按在旧位置。
- 输入回传（Mac `InputInjector.handle` `:921`）：Windows 鼠标事件经 `0x04` 发回，
  Mac 用 `CGEvent.mouseMoved` 把光标重放到虚拟屏坐标，又把 Mac 光标拉回副屏。

结果：两端都不放行，Mac 光标被输入回传拉回虚拟屏、Windows 光标钉在旧位置，
体感即「鼠标被困在副屏」。这是设计边界（`research/FIX-01-cursor.md` 已列光标
形状/跨屏为未做项），不是某个判断写反。

要真正解决需协议级改动：Mac 检测鼠标离开虚拟屏时发明确「离开」事件，Windows
释放光标控制权；并加「边界穿越」把物理鼠标在正确的屏幕间交接。**协议设计已出稿**：
`research/FIX-05-cursor-crossscreen.md`（扩展 `0x03` 加 state、两端状态机、
滞回防抖、分步落地、需 Mac 确认的点），尚未落地。

## 鼠标「还是 Windows 指针」——已由 `f3027af` 修复

`f3027af` 新增 `0x05` 光标图像包（`[u16 w][u16 h][u16 hotX][u16 hotY][u32 n][BGRA]`），
Mac `CursorImageTracker` 用 `NSCursor.currentSystem` 取位图与热点，
Windows `OnCursorImagePacket` + `ApplyCursorImage` 用 `CreateIconIndirect`
造 32bpp alpha `HCURSOR`，`WM_SETCURSOR` 应用之，无自定义时退回 IDC_ARROW。
`HCURSOR` 创建/销毁统一在 UI 线程（`WM_APPLY_CURSOR`），避免跨线程句柄竞态。
版本错配最多丢自定义光标，`0x03` 位置链路不受影响。

Windows 端实机补验：`f3027af` 的 `ApplyCursorImage` 用了 `CreateDIBSection` /
`CreateBitmap` / `DeleteObject`，但两套构建脚本都漏了 `gdi32`，MSVC 报 LNK2019、
MinGW 报 undefined reference，本机编译直接失败。已补 `#pragma comment(lib,"gdi32.lib")`
与 `-lgdi32`（提交 `6ec0820`），两套工具链重新编译通过；用假服务端发合规 `0x05`
包实跑，GDI 造光标链路无崩溃、`GetCursorInfo` 读到非空光标句柄。

## 卡顿——有量化证据，非主观

`telemetry/mac/d87b16db.json`（08:09 旧数据，但仍反映瓶颈）：

- `peak_fps` median 14 / p95 43（上限 45Hz）：有动静时帧率塌到 14
- `capture_ms` median 7.4 + `encode_ms` median 17.8 ≈ 25.2ms，超过 45Hz 的
  22.2ms 帧预算，编码是瓶颈
- `dropped_total=32450`、`congestion` 13 次、`inflight_max=2`
- `mbps` p95 仅 1.3（目标 180Mbps，静止画面保活拉低）

`ScreenSender.swift` 在途帧超限直接丢帧保实时，这是 dropped 来源。
另 `research/FIX-03-coordinate.md` 记录已知未修项：89Hz 屏配 ~43fps 输出的
2/3 刷新周期跳变。

## 全屏 / 分辨率缩放——已定性（2026-11-10 19:5x 真实全屏联调）

代码侧全屏要素齐备：默认 `fullscreen=true`（`:1268`）、
`PER_MONITOR_AWARE_V2` DPI 感知（`:1505`）、`EnumDisplaySettingsW` 取物理分辨率
（`:1552`）、`SetWindowPos(HWND_TOPMOST)` 兜底。

用户授权启动后跑了一次真实全屏（`--fullscreen --log logs/fullscreen.log`），
端到端出画，日志里点名的四行数值：

```
全屏目标尺寸 2880x1800（显示器物理分辨率）
窗口客户区 2880x1800  窗口矩形 2880x1800
坐标基准: 逻辑 2880x1800（物理 2880x1800，默认对齐物理）
退出方式: Esc / 左键托盘图标 / 右键菜单 / Ctrl+Alt+Q
```

客户区 == 窗口矩形 == 物理分辨率 2880x1800，无边框全屏、1:1、无系统二次缩放。
配合 `呈现器: 输入 2880x1808，只取 2880x1800`，1808 宏块对齐纹理裁到 1800 行
按构造 1:1 映射，比例正常。**当前版本全屏路径本身没有缩放问题**，之前「分辨率
怪/要缩放」最可能来自 `e153f2c` 之前的旧 exe（坐标基准还打「自动 2x」）或落到
窗口模式（1440x900 客户区承载 2880x1800 视频，2:1 缩小发糊），不是全屏逻辑缺陷。

同次联调还闭环了另外两项：

- **延迟统计**：`d425094` 修复后端到端 `附加延迟` 不再恒 0，实测 0.0 到 6.4 ms
  真实波动（窗口内相对最快帧），此前「0.0ms 未修好」的遗留可关闭。
- **输入回传 `0x04`**：真机 `输入 N` 计数增长，链路工作。静止桌面 `光标+0`
  属预期（Mac 仅指针位移超阈值才发 `0x03`）。
- 稳定 20 秒，`解码失败 0` 全程保持，静止桌面约 12 至 13 fps、0.5 至 0.6 Mbps。
