> 现象来源：用户在 Windows 上看到「峰值帧率 13.5」，认为帧率过低，要求解决。

## 一、Mac 侧同时段实测（同一连接，可作为对照）

Mac 发送端（smooth 2240x1400@60，pid 7349，虚拟屏 id=14）日志：

```
采集 2540  峰值 57fps  空闲 8748  发送 0   丢弃 0  在途 0  编码延迟 15.2 ms
采集 2562  峰值 57fps  空闲 8830  发送 3   丢弃 0  在途 0  编码延迟 16.3 ms
采集 2587  峰值 57fps  空闲 8911  发送 24  丢弃 0  在途 0  编码延迟 15.6 ms
采集 2611  峰值 57fps  空闲 8992  发送 24  丢弃 0  在途 0  编码延迟 15.9 ms
```

换算：
- `发送 24`/2 秒 ≈ **12 fps 实际发送**，与 Windows 显示 13.5 基本一致。
- `采集` 增量约 12/s，`空闲` 增量约 27/s —— 说明画面基本静止，SCK 大多在回调 idle 帧。
- `峰值 57fps` 是 Mac 侧「近 10 秒窗口最大值」，代表**此前有运动时达到过 57fps**。
- `丢弃 0`、`在途 0`：没有拥塞丢帧。

对照实验（Mac 侧用 motionloader 造真实动画负载时）：**58fps 稳定、发送 114~116/2 秒、
编码 16~18ms、丢弃 0**。即运动时能跑满。

## 二、Mac 侧结论

`13.5fps` **与 Mac 实际发送速率一致，属静止桌面的正常值**，不是丢帧或故障。
ScreenCaptureKit 是变化驱动：屏幕不动就不产生 complete 帧，只产生 idle 帧，
因此静止时帧率天然很低；一旦拖动窗口/滚动/播放视频，会立刻升到 50+。

## 三、请 Windows 侧确认/回应（各一条即可）

   （我方理解是你新增的 `recentFps[5]` 近 ~10 秒最大值；请确认。）

3. **运动时的对照**：请在 Windows 上拖动一个窗口或滚动网页 10 秒，回传那一段日志的
   `峰值 fps` / `解码 N(+N)`，看是否升到 50+。若仍停在 13 附近，才说明链路真的丢帧，
   再排查。
4. 若确认是静止正常值，**建议在 Windows 日志/UI 里把「峰值帧率」和「当前帧率」分开显示**，

## 六、后续（2026-11-11 Mac 侧补充）：找到了真 bug，不只是静止值

上面把 13.5 归因为「静止正常」，但继续排查发现**同时存在一个真 bug**：运动时 Mac
采集 57fps、编码正常，`发送` 却为 0、`Mbps` 0，用户看到画面冻结、帧率虚低。

根因：`receiveLoop` 里 `done || err != nil` 就把 `connected` 置 false。接收侧 EOF
只代表对端不再发数据（可能是半关闭），发送方向仍可用；一置 false 就彻底停发视频，
直到对端重连——所以出现「连着一会儿就不动，过一阵重连又动」的现象。

已修（提交 `31421d9`）：接收侧结束只记日志、不再停发送；断开交由发送完成回调判定；
`.cancelled` 与发送失败补充日志便于定位。

实测修复后（同机运动负载）：`发送 88→115→116→115`/2 秒 ≈ 57fps 持续、峰值 58fps、
`丢弃 0`、编码 13~16ms。

所以你方若仍看到「帧率低、画面冻结」，请先确认 Mac 端已更新到 `31421d9` 之后并重启。
静止时 ~12~13fps 仍是正常值（SCK 变化驱动），拖动窗口/滚动应升到 50+。
