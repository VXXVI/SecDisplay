# 联调观察：Mac 切 smooth 档后两端分辨率不一致（2026-11-10 21:4x）

用户授权启动接收端配合 Mac 联调。窗口化 `10.10.10.1:9922 2880 1800 --windowed`，
端到端出画，`解码失败 0` 全程保持，包数稳定增长约 14 至 15 fps。
但日志暴露一个此前没出现过的分辨率组合，需要两端约定。

## 现象

```
目标 10.10.10.1:9922  分辨率 2880x1800  窗口  重连 开
解码器就绪 2880x1800（硬件）
  可用输出[0] 子类型 3231564E 尺寸 2240x1408
解码器按 2240x1408 输出（比请求的 2880x1800 高），呈现时裁掉多余行
呈现器: 输入 2240x1408，只取 2880x1800
包 27  解码 26(+26)  2.4 Mbps  附加延迟 3.0 ms  解码失败 0
```

之前稳定跑的是 `2880x1808`（sharp/balanced 档的宏块对齐），这次是 `2240x1408`。

## 根因：Mac 侧切到了 smooth 档

`prototype/mac/Sources/ScreenSender.swift:1157-1180` 的 `SECDISPLAY_PRESET`：

| 档位 | cfg.width x height | logical | captureHz |
|---|---|---|---|
| sharp | 2880x1800 | 1440x900 | 40 |
| balanced（默认） | 2880x1800 | 1440x900 | 45 |
| smooth | **2240x1400** | 1120x700 | 60 |
| fast | 1920x1200 | 960x600 | 60 |

`2240x1408` = smooth 档 `2240x1400` 按 H.264 宏块 16 对齐（1400 → 1408）。
`867ad67`（修 preset.sh 与 run.sh 衔接，切档走统一启动路径）之后切档会真正生效，
所以这次 Mac 发来的实际是 smooth 档。Windows 端命令行仍写死 `2880 1800`，
两边对不上。

## 影响（Windows 端代码层面）

1. **呈现器裁边方向反了**。`SecDisplayReceiver.cpp:1072-1077`：
   `RECT src{0,0,width_,height_}` 写死取显示尺寸（`2880x1800`）。
   这段当初只为「硬解输出比显示高几行」（1808 vs 1800）设计，即 src 比 dst 大、
   裁掉多余行。现在 src=`2240x1408` 比 dst=`2880x1800` 小，source rect 右下角
   超出纹理范围，行为未定义，可能拉伸变形、裁掉画面或留黑边。日志里
   「只取 2880x1800」这句在这种反向情况下名不副实。
   `srcW_/srcH_` 来自解码器输出（`:1081-1085`），`width_/height_` 来自
   `cfg.width/height`（`:991`、`:1045-1046`），两者确实不一致。

2. **坐标基准对不上**。`坐标基准: 逻辑 2880x1800（默认对齐物理）` 按命令行走，
   而 Mac smooth 档虚拟屏是 `2240x1400`（逻辑 1120x700）。`0x03` 光标位置与
   `0x04` 输入回传的换算分母会偏大，光标显示偏移、点击回传放大。

3. **视频本身能解能显**。`解码失败 0`、帧率约 14 至 15 fps、`附加延迟` 真实波动，
   说明码流链路没断，问题只在尺寸语义与呈现映射。

## 需要 Mac 侧定夺的两条路

**A. 两端统一档位（推荐先这样）**：Mac 切档时，Windows 端启动参数同步改成该档
分辨率（smooth 用 `2240 1400`，fast 用 `1920 1200`）。改动只在启动脚本/命令，
代码不动，最快恢复 1:1。需要一份「档位 → 两端分辨率」的对照，或让发送端
在握手里把 cfg.width/height 告知接收端（协议小改）。

**B. 接收端自适应**：Windows 端不再依赖命令行 `width/height` 定死显示尺寸，
改从解码器实际输出尺寸推导，并按「src 与 dst 谁大」分情况设 source rect：
- src 比 dst 大：取 dst 大小裁掉多余（现有逻辑）
- src 比 dst 小：把整个 src 作为 source rect，让 VideoProcessor 缩放到 dst（或按档位缩放全屏窗口）
坐标基准也随实际解码尺寸走。

B 更通用但要动呈现器与坐标基准，且要决定「窗口/全屏尺寸是否随档位变」，
牵涉 `EnumDisplaySettings` 全屏逻辑，建议两端商量后再动。
