## 实机验证

命令（窗口化模式，不占全屏，不依赖 Mac 在线）：

```cmd
SecDisplayReceiver.exe 10.10.10.1 9922 2880 1800 --windowed --log logs/tray_smoke.log
```

关键日志：

```
退出方式: Esc / 左键托盘图标 / 右键菜单 / Ctrl+Alt+Q
窗口客户区 1440x900  窗口矩形 1466x971
坐标基准: 逻辑 2880x1800（物理 2880x1800，默认对齐物理）
连接 10.10.10.1:9922 ...
连接失败 10061
```

结论：

- 托盘图标注册成功。日志打出「退出方式」那一行，说明 `TrayCreate` 里的 `Shell_NotifyIconA(NIM_ADD)` 走到了，没有出现「托盘图标添加失败」。
- 全局热键注册成功。没有打出「全局热键 Ctrl+Alt+Q 注册失败」，`RegisterHotKey` 返回有效。
- 窗口化模式正常，`坐标基准` 与 `e153f2c` 的修复一致，默认对齐物理 2880x1800。
- 自动重连正常。Mac 发送端未在 9922 监听，日志按预期循环「连接失败 10061 / 连接 ...」。

统一退出路径：向窗口投递 `WM_CLOSE`，进程干净退出，无残留进程，日志尾部走到「网络循环退出」。`RequestQuit -> WM_CLOSE -> 清托盘/热键/线程` 这条链路在实机上通了。

## 代码审查发现

对 `bcceb45` 新增段（`SecDisplayReceiver.cpp` 约 185-245、284-293、1148-1193、1306-1469、1566-1669 行）做了两轮核对，第二轮由子代理独立交叉验证，纠正了第一轮的几处判断。

**一处阻断级风险（建议 Mac 侧优先处理，尚未在已连接态验证）**

退出清理段的顺序是 `TrayRemove -> UnregisterHotKey -> g_alive=false -> net.join()`。`NetworkLoop` 里收流线程阻塞在 `RecvAll` 的 `recv(s, ...)` 上，而 `RecvAll` 没有设置 `SO_RCVTIMEO`，socket 也只在连接断开后才 `shutdown/closesocket`（`:1461-1462` 排在 `recv.join()` 之后）。`g_sock` 只被 `SendInputPacket` 用于 send，`connAlive` 仅由 recv 线程退出后置假，都救不了这个阻塞。

触发条件是**已经连上 Mac 但链路静默**（静止画面、Mac 暂停、TCP 半开）。持续推帧时 `recv` 会返回、循环下一轮检查 `g_alive` 就退了，反而不会挂；恰恰是没数据时 `recv` 永久阻塞，`net.join()` 一直等它返回。此时 `WM_CLOSE`（`:1150-1154`）不 `DestroyWindow` 也不交 `DefWindowProc`，全屏置顶窗口冻结盖屏，而托盘图标和全局热键已被 `TrayRemove`/`UnregisterHotKey` 摘掉，用户没有逃生口，只能强杀。这跟 `bcceb45`「兜底强退」的目标正好相反。

本次冒烟测试是在「连接失败 / 自动重连」分支退出的，那一段有 `Sleep(2000)` 且每轮会重新检查 `g_alive`（`:1326-1331`、`:1307`），所以秒退。**已连接态的退出没有覆盖到**，等 Mac 发送端恢复后建议专门复测一次：连上且画面静止时按 `Ctrl+Alt+Q`，看进程是否在 1 秒内退出。

可行的修法（供参考，未改）：退出前从主线程对 `g_sock` 调 `shutdown(SD_BOTH)` 打断阻塞 recv，或给 `RecvAll` 加 `SO_RCVTIMEO`／改用 `select` 轮询 `g_alive` 后再 join。

**其它发现**

- 严重：四个退出入口（托盘左键、菜单退出、`Ctrl+Alt+Q`、Esc）全部汇入 `WM_CLOSE` 同一收尾路径，等于把上面这个挂起缺陷的触发面扩到全部退出方式。
- 一般：`TrayCreate` 之后的早退（`:1597`、`:1602`，呈现器初始化失败或 `WSAStartup` 失败时直接 return）会跳过 `TrayRemove`，留托盘残影，与 `:1656` 注释目标相悖。早退应统一走单一收尾。
- 一般：`connect()`（`:1326`）阻塞无超时，黑洞网络下约 20 秒量级，`g_alive=false` 打断不了，退出体感不可控。
- 一般：托盘提示、菜单、关于框用 A 版 API 传 UTF-8 中文字面量（`:216-218`、`:236-239`、`:1174-1179`），中文 Windows 的 ACP 为 CP936，A 版按 CP_ACP 解码会乱码。仅影响可读性，不动退出逻辑。
- 一般：`WM_CLOSE` 只 `PostQuitMessage` 不销毁窗口，`WM_DESTROY` 分支在正常退出路径不可达；`TrayRemove` 幂等、窗口由系统回收，无实际泄漏，与「统一退出」语义略有出入。

**核查通过、无需改动的部分**

- `NOTIFYICONDATAA` 零初始化覆盖全部字段，`cbSize / hWnd / uID / uFlags / uCallbackMessage / hIcon / szTip` 都设了，用 `IDI_APPLICATION` 省资源文件可行。`hIcon` 是系统共享图标，不 `DestroyIcon` 是对的。
- `strncpy` 写 `szTip` 后手动补 `'\0'`，无越界，64 或 128 字节的 `szTip` 都放得下，兼容 MinGW 与 MSVC。
- `TrayRemove` 幂等：`g_trayAdded` 标志保证 `NIM_DELETE` 只发一次，`WM_CLOSE` / `WM_DESTROY` / 退出清理段重复调用无害。
- `RegisterHotKey` 与 `UnregisterHotKey` 配对，注册失败时仍调用 `UnregisterHotKey` 是安全的（对未注册 id 返回错误码，无副作用）。
- `HOTKEY_QUIT_ID=1` 与三个 `ID_TRAY_*`（1001/1002/1003）分属不同命名空间，不冲突。
- `TrayShowMenu` 有 `CreatePopupMenu / AppendMenuA / SetForegroundWindow / TrackPopupMenu / DestroyMenu` 完整配对，前置激活避免菜单被置顶窗口盖住。未带 `TPM_RETURNCMD`，靠 `WM_COMMAND` 派发，忽略 `TrackPopupMenu` 返回值是正确用法。
- 未调 `NIM_SETVERSION` 即停留 version 0，`lParam` 为鼠标消息，`LOWORD(l)` 判 `WM_LBUTTONUP/WM_RBUTTONUP` 正确。若日后改 `NIM_SETVERSION_4`，须同步改 `WM_CONTEXTMENU` / `GET_X_LPARAM(wParam)` 解析。
- `RequestQuit` 用 `PostMessageA(g_hwnd, WM_CLOSE)`，`g_hwnd` 在 `:1566` 赋值且存活期不销毁，安全。`cursorThread` 的 `Sleep(4)` 循环在 `g_alive=false` 后 4ms 内退出，但它排在 `net.join()` 之后，救不了主流程。
- MinGW 忽略 `#pragma comment(lib)`，但默认库集含 `-lshell32/-luser32`，`Shell_NotifyIconA`/`RegisterHotKey` 仍可解析；MSVC 侧 pragma 有效。两条工具链都能链过（`build.bat` 已实测，MinGW 侧未在本轮实跑，CI 可覆盖）。

**一处行为提示（非 bug）**

`ID_TRAY_ABOUT` 的 `MessageBoxA` 是模态框，自带嵌套消息泵，弹框期间外层 `GetMessage` 暂停，托盘和热键暂时无响应，点掉「关于」即恢复。recv/watch/cursor 在独立线程照常运行，不会死锁。

## 另修：`start.bat` 去掉 UTF-8 BOM

`start.bat` 是双击全屏入口，文件头带 BOM（`EF BB BF`）。在 GBK 控制台下 cmd 把首行读成 `锘@echo off`，`@echo off` 失效，运行时会逐行回显命令，界面很乱。这和之前 `check.bat` 踩过的是同一个根因。

改动仅去掉 BOM 三个字节，CRLF（29 行）和其余内容不变。用临时副本（占位 exe + 跳过真实启动）完整跑了一遍：`@echo off` 生效，无命令行回显，中文提示正常，退出码 0。

## `207f1a5` 修复复测（2026-11-10 17:55）

Mac 侧根据本文档的阻断级风险推送了 `207f1a5`（Windows: 修已连接态退出卡死），改法与报告里给的两条建议一致，并做了双保险：

- `RecvAll` 用 `SO_RCVTIMEO(500ms)` 区分超时与真断开，`g_alive=false` 时立即返回
- 连接建立后给 socket 设 `SO_RCVTIMEO`
- 退出清理段在 `net.join()` 前先 `shutdown(g_sock, SD_BOTH)` 掐断阻塞 recv
- `g_alive` 前移到全局区顶部，供底层函数读取

**这次专门覆盖了之前没验的「已连接态」**，用本机假服务端精确复现卡死场景：`127.0.0.1:9922` 接受连接后不发任何数据，模拟链路静默。接收端日志确认走到「已连接 / 解码器就绪 / 硬解」并连续「无新帧 N 轮，重新请求关键帧」，收流线程正阻塞在等 4 字节长度头，这正是修复前 `net.join()` 会永久挂起的状态。

| 对照 | 退出触发 | 结果 |
|---|---|---|
| 第一组（连上 6 秒后） | `WM_CLOSE` | 135 ms 干净退出，无残留进程，日志走到「网络循环退出」 |
| 第二组（连上 3 秒、监控未打首轮） | `WM_CLOSE` | 77 ms 干净退出，无残留进程 |

第二组假服务端在 `2.627s` 观察到 `PEER_CLOSED`，即接收端退出瞬间对端连接被关闭，直接印证 `shutdown(SD_BOTH)` 掐断了阻塞的 `recv`，收流线程立即返回。`WM_CLOSE` 是 `Esc` / 托盘 / `Ctrl+Alt+Q` 三条退出路径汇入的同一收尾点，因此这三条在已连接态都随之打通。

`build.bat`（MSVC）与 `build-mingw.bat`（MinGW）均编译通过，CI 三个 job 全绿（build-windows / build-mac / telemetry-consistency）。

**结论：报告里那处阻断级风险已由 `207f1a5` 修复并在实机验证生效，可以关闭。**
