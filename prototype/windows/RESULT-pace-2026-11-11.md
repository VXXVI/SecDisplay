# RESULT（Windows）：可选一帧抖动缓冲 `--pace` 实现与 A/B

> 对应：`research/SYNC-fps-2026-11-11.md`、`research/TASK-mac-frame-pacing-2026-11-11.md`
> 执行提交号：`0c12f1f`（代码与本文档同批）
> 执行端：Windows 侧
> 日期：2026-11-11

## 一、为什么做

此前已确认：Windows 侧上屏没有额外丢帧，源间隔与上屏间隔逐项吻合；
剩余约 5% 的双倍帧间隔来自 Mac 发送侧的帧节奏。
完全在 Windows 侧抹平这段抖动，只有加缓冲一条路，代价是延迟增加约一帧。

## 二、实现

新增可选开关 `--pace`，默认关闭，不改变现有低延迟行为。

- 呈现线程保留一个最多 3 帧的小队列，起步先预填 1 帧。
- 目标节拍由源端平均帧间隔决定，并**吸附到显示器刷新周期的整数倍**，
  避免垂直同步在节拍之上再量化一次。
- 只在源帧率低于刷新率 60% 时启用；高帧率内容自动保持即时上屏。
- 节拍以「本次上屏开始时刻」为基准，不把 `Present` 的阻塞时长叠加进去。
- 队列溢出时丢最旧帧，单独计入 `节拍丢帧`，不与普通 `呈现丢帧` 混淆。
- 新增日志字段：`节拍 X ms`、`节拍丢帧 +N`。

启动日志会明确打印：

```
抖动缓冲: 开（一帧缓冲，自适应节拍，增加约一帧延迟）
```

## 三、A/B 数据（首版，未吸附刷新周期）

同一 exe，默认与 `--pace` 交替各 20 秒，共两轮，取末尾 7 个窗口平均：

| 模式 | 当前 fps | 呈现丢帧 | p50 | p95 | 节拍 | 节拍丢帧 |
|---|---|---|---|---|---|---|
| 默认 | 33.8 | 0 | 31.8 ms | 51.2 ms | 0 ms | 0 |
| `--pace` | 34.7 | 0 | 34.4 ms | 41.2 ms | 30.2 ms | 115 |

结论：

- p95 从 51.2ms 降到 41.2ms，约改善 20%，抖动明显收敛。
- 帧率基本不变，p50 略升，说明输出更接近稳定节拍。
- `节拍丢帧` 115 次/约 40 秒，是缓冲为维持节拍主动丢弃的早到帧，属于预期代价。

## 四、吸附刷新周期后的预期

首版节拍 30.2ms 不是 90Hz（11.1ms）的整数倍，垂直同步仍会把它量化成 2/3 个周期。
已改为 `ceil(平均帧间隔 / 刷新周期) × 刷新周期`：

- 约 36fps 源在 90Hz 屏上会吸附到 3 个周期 = 33.3ms，即稳定 30fps 节奏。
- 预期 p50/p95 都收敛到 33.3ms 附近，代价是偶尔丢掉 36fps 的早到帧。

**该版本的实测被 Mac 侧监听端口消失阻塞**，恢复连接后补测。

## 五、使用方式

```
SecDisplayReceiver.exe 10.10.10.1 9922 2240 1400 --pace
```

不加 `--pace` 时行为与之前完全一致，延迟最低。
若更看重画面均匀，可以加 `--pace`，代价是约一帧延迟（30fps 内容约 33ms）。
