## 三、任务 5（点击错位）与任务 6（不是全屏）证据回传

Mac 侧任务单要求「结论回来前不要盲改坐标代码」，本端遵守，只回传证据，不改任何坐标逻辑。
以下数值取自 `evidence/windows-2026-11-10/fullscreen.log`（早先真实全屏联调，已上传）：

```
全屏目标尺寸 2880x1800（显示器物理分辨率）
窗口客户区 2880x1800  窗口矩形 2880x1800
坐标基准: 逻辑 2880x1800（物理 2880x1800，默认对齐物理）
退出方式: Esc / 左键托盘图标 / 右键菜单 / Ctrl+Alt+Q
呈现方式: 垂直同步（均匀）
可用输出[0] 子类型 3231564E 尺寸 2880x1808
呈现器: 输入 2880x1808，只取 2880x1800
```

那次是真全屏（客户区 == 窗口矩形 == 物理分辨率，1:1），四行判据齐全。
但用户睡前反馈「目前还不是全屏」，与这次日志不是同一时刻，需要区分：
- 若用 `start.bat` / `monitor.bat` / `diag.bat` 启动，三个 bat 都带 `--fullscreen`，
  且 `abe8e29` 后 `SECDISPLAY_W/H` 默认 2240 1400。
- 若直接双击 exe 或命令行漏了参数，会落到默认窗口化，客户区变成 1440x900，
  这正是「不是全屏」的常见原因。`evidence/` 里窗口化日志的客户区恒为 1440x900，可对照。
- 本端近期验证实例都用 `--windowed`（便于远程取证），不代表用户那次启动方式。

**错位方向**：需要用户在副屏左上角与右下角各点一次、描述菜单/点击落在哪，
这是任务 5 明确要的现场描述，本端单靠日志给不出，属需用户配合的阻塞项。
本端能补充一个静态线索：`ClientToVideo` 用 `g_coordW/H` 做分母，`g_coordW/H` 默认取
命令行 `cfg.width/height`；Mac 切 smooth(2240x1400) 而 Windows 仍带 2880 1800 时，
分母偏大会让回传坐标放大约 22%~29%。`abe8e29` 把 bat 默认改 2240 1400 已缓解这一路径。
但 Mac 侧已派子代理核查坐标闭环，本端不改代码，等结论。

## 四、解码失败与延迟的既有结论（供 Mac 侧参考，避免重复定性）

- `解码失败` 在全部上传日志里恒为 0（17 份逐份核对，见 `evidence/.../README.md`）。
  `abe8e29` 关于「FRAME_SIZE 与 SPS 不符导致 ProcessInput FAILED 累加」的因果，
